# Personal Messenger — Design Spec

**Date:** 2026-11-02
**Status:** Approved by owner
**Author:** Buffy (design session with owner)

---

## 1. Context

A private messenger for one owner and a small group of friends (assumed ≤ 20 accounts).
The owner is on a Windows laptop; friends are on Android phones. There is no public signup —
accounts come from invite codes.

Two behaviours define the product:

1. **Desktop presence without disruption.** The Electron app runs continuously in the background
   (tray only). When a message arrives it raises a small glass card in a screen corner for 5–10 s,
   then disappears. It must not steal focus and must not be suppressible by Windows Focus Assist.
2. **Same beautiful thing on both platforms.** One glassmorphism design, implemented once, running
   in Electron and in an Android APK.

Everything is free to operate: Render free web service, Turso free database, Firebase Cloud
Messaging free tier.

### Goals

- Text chat: 1:1 direct messages and group conversations.
- Instant delivery while a client is connected; Android notification when the app is not.
- Persistent history, catch-up after disconnect, no duplicate messages on retry.
- Desktop corner popup window, clickable, configurable corner and duration.
- One shared UI codebase rendering identically on desktop and mobile.
- ₹0/month running cost.

### Non-goals (v1)

- Photos, voice notes, files. The schema reserves an `attachments` table; nothing else is built.
- Reactions, replies, message editing, search, conversation creation UI beyond the initial seeded
  group + DMs.
- End-to-end encryption. Transport is TLS; the server can read message bodies. Accepted for a
  friend-group deployment; recorded here explicitly so it is not mistaken for a guarantee.
- Voice/video calls, read-receipt privacy settings, multi-device sync beyond "same account, two
  platforms".

## 2. Hosting constraints that shaped this design

Verified against Render's documentation on 2026-11-02.

| Constraint | Consequence for this design |
|---|---|
| Free web service spins down after **15 min without inbound traffic**. An idle open WebSocket does **not** count; only WS *messages* do. Cold start ≈ 60 s. | Clients send an app-level WS `ping` every 30 s, which keeps the service awake while anyone is connected. An external cron pings `GET /healthz` every 10 min as a backstop for when nobody is online. |
| Free filesystem is **ephemeral**; persistent disks are not available on free; Render's free Postgres is deleted 30 days after creation. | Database is external: **Turso** (hosted libSQL/SQLite). |
| 750 free instance-hours per workspace per month (a 31-day month is 744 h). | Exactly one always-on service. No separate worker, no separate cron service, no Redis. Everything lives in the single Node process. |
| 0.1 CPU / 512 MB RAM. | Text only. No image processing, no in-memory upload buffering, no native module compilation. Passwords use `node:crypto` scrypt, not argon2. |
| Instances restart at will; deploys send SIGTERM with a 30 s grace window. Sockets drop. | Every client reconnects with exponential backoff and catches up via `GET /sync?since=<messageId>`. Delivery is never fire-and-forget. |

**Turso** free plan: 5 GB storage, 500M rows read/month, 10M rows written/month, databases stay
responsive regardless of inactivity, no expiry. Ownership note: Turso was acquired by Supabase in
Oct 2026 with a public commitment that the service continues; the schema is plain SQLite, so a move
to Render Postgres, Neon, Aiven or a VPS later is a migration, not a rewrite.

The alternative host considered and rejected by the owner: Oracle Cloud always-free ARM VM (no
spin-down, no hour cap). It remains the recommended upgrade if Render's limits start to hurt.

## 3. System architecture

```
┌───────────────────┐                    ┌──────────────────────┐
│  Electron (Win)   │◄──── wss ─────────►│                      │
│  tray + popup     │                    │  Node/TS service     │──► Turso (libSQL)
└───────────────────┘                    │  Fastify + ws        │
┌───────────────────┐                    │  Render free (Docker)│──► FCM HTTP v1 ──► phone
│  Android APK      │◄──── wss ─────────►│                      │
│  Capacitor shell  │                    └──────────────────────┘
└───────────────────┘
```

Repository layout (npm workspaces; npm chosen for frictionless Electron and Gradle interop):

```
apps/
  server/            Node 22, Fastify, ws, @libsql/client
  desktop/           Electron main + preload, electron-builder config
  mobile/            Capacitor shell; android/ Gradle project generated by `npx cap add android`
packages/
  ui/                shared React app (Vite): chat screen, popup screen, design system
  shared/            types, zod schemas, API client, socket protocol, transport interface
docs/superpowers/specs/
```

`packages/ui` is consumed as source by both Vite (desktop renderer) and Capacitor's web build, so
there is exactly one implementation of every screen. `apps/mobile` holds only the native shell and its Capacitor config; it does not contain UI code.

## 4. Data model (Turso / SQLite)

```sql
CREATE TABLE IF NOT EXISTS users (
  id            TEXT PRIMARY KEY,                    -- uuid v4
  username      TEXT NOT NULL UNIQUE COLLATE NOCASE,
  display_name  TEXT NOT NULL,
  password_hash TEXT NOT NULL,                       -- scrypt$N$r$p$salt$hash
  accent        TEXT NOT NULL,                       -- avatar tint, hex
  created_at    INTEGER NOT NULL,                    -- epoch ms
  last_seen_at  INTEGER
);

CREATE TABLE IF NOT EXISTS sessions (
  id          TEXT PRIMARY KEY,                      -- refresh-token family id
  user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash  TEXT NOT NULL,                         -- sha256(refresh token)
  platform    TEXT NOT NULL,                         -- 'android' | 'desktop'
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL,
  revoked_at  INTEGER,
  replaced_by TEXT
);

CREATE TABLE IF NOT EXISTS conversations (
  id         TEXT PRIMARY KEY,
  kind       TEXT NOT NULL CHECK (kind IN ('dm','group')),
  title      TEXT,
  dm_key     TEXT UNIQUE,                            -- sorted user ids joined by ':', dm only
  created_by TEXT REFERENCES users(id),
  created_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS members (
  conversation_id      TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  user_id              TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  joined_at            INTEGER NOT NULL,
  last_read_message_id INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (conversation_id, user_id)
);

CREATE TABLE IF NOT EXISTS messages (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  sender_id       TEXT NOT NULL REFERENCES users(id),
  body            TEXT NOT NULL,
  client_id       TEXT NOT NULL,
  created_at      INTEGER NOT NULL,
  deleted_at      INTEGER
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_messages_client ON messages(sender_id, client_id);
CREATE INDEX IF NOT EXISTS idx_messages_conv ON messages(conversation_id, id);

CREATE TABLE IF NOT EXISTS devices (
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  platform     TEXT NOT NULL CHECK (platform IN ('android','desktop')),
  fcm_token    TEXT,
  created_at   INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_devices_token
  ON devices(fcm_token) WHERE fcm_token IS NOT NULL;

CREATE TABLE IF NOT EXISTS invites (
  code       TEXT PRIMARY KEY,
  created_by TEXT REFERENCES users(id),
  expires_at INTEGER,
  used_by    TEXT REFERENCES users(id),
  created_at INTEGER NOT NULL
);
```

Design notes:

- **`messages.id` is the ordering cursor.** Autoincrement, server-assigned, monotonic. No client
  clocks are trusted for ordering, so clock skew cannot reorder a conversation. Clients sort by
  `id`, display by `created_at`.
- **`(sender_id, client_id)` unique** makes a retry after a dropped connection idempotent: resending
  the same `clientId` returns the existing row instead of creating a second message.
- **`dm_key`** prevents two DM threads between the same pair.
- **`members.last_read_message_id`** is the read-receipt cursor, not a boolean, so it stays correct
  after catch-up sync.
- Migrations run at boot as `CREATE TABLE IF NOT EXISTS` + a `schema_version` row, because the free
  tier offers no shell access. Each future migration is appended to a numbered array in `db/migrate.ts`.

## 5. HTTP API

All bodies JSON, validated with zod. Auth is a bearer access token except where noted.

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/register` | `{inviteCode, username, password, displayName}` → user + tokens. Invite marked used in the same transaction. |
| POST | `/auth/login` | `{username, password, platform}` → `{accessToken, refreshToken, user}` |
| POST | `/auth/refresh` | `{refreshToken}` → rotated pair; old token revoked, `replaced_by` set. Reuse of a revoked token revokes the whole family. |
| POST | `/auth/logout` | Revokes the session family. |
| GET | `/me` | Current user. |
| GET | `/conversations` | Conversations with last message, unread count, member list. |
| GET | `/messages?conversationId=&before=<id>&limit=50` | Backwards pagination. |
| GET | `/sync?since=<messageId>` | Catch-up: all messages in the caller's conversations with `id > since`, grouped, capped at 500 with `hasMore`. |
| POST | `/devices` | `{platform, fcmToken}` — upsert on token. |
| DELETE | `/devices/:id` | Unregister on logout. |
| GET | `/healthz` | Unauthenticated liveness probe for the keep-alive cron. **Must not touch the database** so a Turso hiccup does not read as a dead server. |

Access token: 15 min JWT (`sub`, `sid`). Refresh token: opaque 32-byte random, 30 days, stored only
as a SHA-256 hash, rotated on every use.

Limits: message body 1–4000 characters after trim. Login 10/min/IP. Register 5/hour/IP. Send 60/min
per user. In-memory limiters — correct because there is exactly one instance.

Errors are `{error: {code, message}}` with stable codes (`INVALID_CREDENTIALS`, `INVITE_INVALID`,
`NOT_A_MEMBER`, `RATE_LIMITED`, `VALIDATION`).

## 6. WebSocket protocol

Connect: `wss://<host>/socket?token=<accessToken>`. Token validated before upgrade; failure closes
with code `4401`. On connect the server loads the user's conversations and joins those rooms — no
global broadcast, so a message can never leak to a non-member.

Client → server:

```jsonc
{ "t": "send",   "clientId": "uuid", "conversationId": "uuid", "body": "hi" }
{ "t": "typing", "conversationId": "uuid", "state": true }
{ "t": "read",   "conversationId": "uuid", "messageId": 412 }
{ "t": "ping",   "ts": 1730000000000 }        // every 30 s; also keeps Render awake
```

Server → client:

```jsonc
{ "t": "ready",    "user": {...}, "conversations": [...], "cursors": { "<convId>": 411 } }
{ "t": "ack",      "clientId": "uuid", "message": { "id": 412, ... } }
{ "t": "msg",      "message": { "id": 412, ... } }
{ "t": "typing",   "conversationId": "uuid", "userId": "uuid", "state": true }
{ "t": "read",     "conversationId": "uuid", "userId": "uuid", "messageId": 412 }
{ "t": "presence", "userId": "uuid", "online": true, "lastSeenAt": 1730000000000 }
{ "t": "pong",     "ts": 1730000000000 }
{ "t": "error",    "code": "NOT_A_MEMBER", "clientId": "uuid" }
```

Send path, in order:

1. Validate membership and body.
2. Insert into `messages` (idempotent on `(sender_id, client_id)`). The row is durable before anyone
   is told it exists.
3. Send `ack` to the sender with the server id; the sender's optimistic bubble resolves.
4. Fan out `msg` to other members' live sockets.
5. For each member with no live socket, send one FCM data push per registered Android device.

Typing is throttled server-side to one event per user per conversation per 2 s and is never stored.

Presence: `online` broadcast on connect/disconnect; `last_seen_at` written on disconnect. A user with
two connected clients (laptop + phone) counts online until both drop.

## 7. Authentication and security

- Passwords: `node:crypto` `scrypt` (`N=16384, r=8, p=1`), 16-byte salt, 64-byte key, compared with
  `timingSafeEqual`.
- Token storage: Electron keeps the refresh token encrypted with `safeStorage` (DPAPI on Windows) and
  the access token in memory. Android uses `@capacitor/preferences`; accepted for a friend-group app,
  documented as not hardware-backed.
- CORS: bearer tokens only, no cookies anywhere, so `Access-Control-Allow-Origin: *` is used and is
  safe here. There is no credential-bearing request that a wildcard could leak.
- WS upgrade refuses requests without a valid token; no token in the URL is logged (query redaction
  filter on the logger).
- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; preload exposes a narrow,
  explicitly enumerated IPC surface. A CSP forbids remote code in the renderer.
- Rate limits and body caps as in §5. The server never returns another user's refresh state.
- Secrets live only in Render environment variables and never in the repo or a client bundle.

## 8. Desktop (Electron)

**The main process owns the single WebSocket.** Two reasons: the app must keep receiving while its
main window is closed (tray only), and there must be one socket per machine, not one per window.

The shared UI consumes a `ChatTransport` interface from `packages/shared`:

```ts
interface ChatTransport {
  connect(): Promise<void>
  on(event: ServerEvent, cb: (payload: unknown) => void): () => void
  send(payload: ClientEvent): void
  status(): 'connecting' | 'online' | 'offline'
}
```

- `IpcTransport` (Electron): renderer → `preload` → `ipcMain` → the main-process socket. Main also
  keeps a small in-memory mirror of unread counts so the tray badge and popup can work with no window
  open.
- `WebSocketTransport` (Android): the UI owns the socket directly.

The renderer does not know which one it has.

**Popup window.** A second `BrowserWindow` loading the same bundle at `#/popup`:

```
frame: false, transparent: true, resizable: false, skipTaskbar: true,
alwaysOnTop: true, focusable: true, hasShadow: false, show: false
```

- Size 380 × 132, margin 16 px, positioned inside `screen.getDisplayNearestPoint(cursor).workArea`
  for the chosen corner (top-right default). Multi-monitor: the display is a setting, defaulting to
  the primary display.
- Shown with `win.showInactive()` so it never takes focus from a game, editor or call.
- Auto-hide after 5–10 s (setting, default 6 s) via a timer that pauses on `mouseenter` and resumes
  on `mouseleave`. A new message while visible re-uses the same window and resets the timer rather
  than stacking windows; up to 3 messages are listed in one card, older ones collapsing to a count.
- Click → reveal and focus the main window, select that conversation, hide the popup. Escape or
  click-through dismisses.
- Rejected alternative: Windows toast notifications, because Focus Assist and full-screen
  presentations suppress them — which defeats the feature. The custom window also gives us the glass
  styling.
- Because a transparent always-on-top window can conflict with exclusive-fullscreen games, the popup
  is skipped while a fullscreen app has focus (best-effort `setAlwaysOnTop(false)` fallback) and this
  is a documented setting.

**Shell behaviour.** Tray icon with menu (Open, Mute 1 h, Popup corner submenu, Popup duration, Start
at login, Quit). Closing the main window hides to tray rather than quitting; Quit really quits.
`setLoginItemSettings` for start-at-login (off by default, opt-in).
`single-instance-lock` so a second launch focuses the existing window.

**Packaging:** electron-builder → NSIS installer for x64 Windows, plus a portable `.exe`. Icons and
app id `com.personalmessenger.desktop`.

## 9. Android (Capacitor)

- Capacitor 7 shell, `appId: app.personalmessenger.mobile`, UI **bundled** into `dist` (no remote URL):
  instant launch, works offline for cached history.
- `@capacitor/push-notifications`: request permission (Android 13+ `POST_NOTIFICATIONS`), register
  with FCM, POST the token to `/devices`. Token refresh re-registers.
- Foreground: live socket, messages appear instantly. Background/killed: Android tears the socket
  down; FCM delivers the notification. This division is intentional and is stated in the UI once
  ("messages arrive as notifications when the app is closed").
- FCM payload carries **both** blocks:
  - `notification: {title: "<display name>", body: "<message>"}` so the system tray renders it with
    no app code when the process is dead.
  - `data: {conversationId, messageId}` so `pushNotificationActionPerformed` deep-links into the
    right conversation.
- `pushNotificationReceived` while foregrounded suppresses the system banner and updates the UI
  instead, so you never get a notification for a chat you are reading.
- Building the APK needs JDK 17 + Android SDK, plus a free Firebase project whose
  `google-services.json` is placed in `apps/mobile/android/app/`. If the SDK is absent on the
  machine, a GitHub Actions workflow builds a debug APK instead of requiring a local Android Studio
  install. Release signing uses a locally generated keystore; friends sideload (enable "install
  unknown apps").
- Permissions kept minimal: `INTERNET`, `POST_NOTIFICATIONS`, `VIBRATE`.

## 10. Shared glass design system

The look is defined once in `packages/ui/src/theme.css` as tokens.

**Backdrop.** An animated aurora: three radial gradients (indigo `#6366f1`, violet `#a855f7`, cyan
`#22d3ee`) on a near-black base `#08080c`, drifting on 40–60 s `transform` keyframes. Without
something colourful behind it, glass reads as flat grey plastic.

**Glass surfaces.**

```css
--glass-fill:    rgba(255, 255, 255, 0.08);
--glass-fill-2:  rgba(255, 255, 255, 0.12);
--glass-border:  1px solid rgba(255, 255, 255, 0.18);
--glass-blur:    blur(20px) saturate(180%);
--glass-shadow:  0 8px 32px rgba(0, 0, 0, 0.37);
--radius-lg:     24px;
--radius-md:     18px;
```

**Performance rule (the important one).** `backdrop-filter` is expensive in mid-range Android
WebViews and in a transparent Electron window. Blur is therefore applied to a small number of *large*
surfaces only — header, composer, popup card, settings sheet. Message bubbles use translucent fills
with a hairline border and no blur. Where `backdrop-filter` is unsupported, `@supports` falls back to
a more opaque fill so the layout never degrades.

**Type and motion.** System UI stack (`-apple-system, "Segoe UI Variable", Roboto`), 15 px body,
13 px metadata, tabular numerals for timestamps. Popup enters with 220 ms
`cubic-bezier(0.22, 1, 0.36, 1)` slide + fade; message rows fade up 120 ms; no animation on scroll
under `prefers-reduced-motion`.

**Layout.** Mobile: conversation list → thread (single column). Desktop: two-pane (list 320 px +
thread), glass rails, no chrome. Both share components; only the grid differs.

**Screens:** Login / Register (invite code), Conversation list, Thread (bubbles, typing dots,
read ticks), Settings (corner, duration, start at login, notifications, sign out), Popup card.

## 11. Deployment

**Render:** Free web service, Docker runtime, region Singapore, health check path `/healthz`, single
instance, auto-deploy from the repo's default branch.

Environment variables:

| Name | Purpose |
|---|---|
| `TURSO_DATABASE_URL` | `libsql://<db>.turso.io` |
| `TURSO_AUTH_TOKEN` | Turso token |
| `JWT_SECRET` | 32+ random bytes |
| `FCM_SERVICE_ACCOUNT_JSON` | Base64 of the Firebase service-account JSON |
| `BOOTSTRAP_INVITE` | First invite code, consumed at first successful register |
| `PORT` | Provided by Render |

`Dockerfile`: `node:22-alpine`, `npm ci`, build server + api types, `node dist/index.js`,
`HEALTHCHECK` on `/healthz`, no dev dependencies in the final layer.

**Keep-alive:** cron-job.org (free) → `GET https://<host>/healthz` every 10 minutes. Documented in
`README.md` as a required setup step with a screenshot-free checklist, since forgetting it is the one
way this deployment silently dies.

**Prerequisite accounts:** Turso, Firebase, Render, cron-job.org. None require a card.

## 12. Testing

- **Server unit/integration (vitest):** auth happy path and failures; refresh rotation and
  reuse-revocation; invite single-use; idempotent resend with the same `clientId`; membership
  enforcement on send/read (a non-member must get `NOT_A_MEMBER`); `/sync` returns exactly the new
  messages and respects the cap; message length limits.
- **WebSocket integration:** two real `ws` clients against a server on an ephemeral port — delivery,
  ack id ordering, typing throttle, read cursor, disconnect/reconnect then `/sync` catch-up with no
  gaps and no duplicates, and a bad token closed with `4401`.
- **DB:** the same `Repo` layer is exercised against a temporary local libSQL file in tests and
  against Turso in staging. If the local file driver proves unusable in this environment, integration
  tests run against a dedicated Turso test database — recorded when decided.
- **UI (vitest + Testing Library):** optimistic send resolves on `ack`, rollback on `error`, unread
  badge, popup card content for 1 vs 3 messages.
- **Manual, required before calling it done:** desktop app receiving a message with its main window
  closed; popup appears over a fullscreen app; click opens the right thread; phone receives a
  notification with the app killed; message sent from phone appears on desktop in under 2 s; a real
  Render cold start after 20 minutes idle, then automatic reconnect without a manual refresh.

## 13. Risks and limitations

| Risk | Mitigation / accepted cost |
|---|---|
| Render free is explicitly not for production; instances restart at will. | Cursor sync + reconnect makes restarts lossless; a 1–2 s blip is possible mid-restart. |
| Cold start ≈ 60 s if the service sleeps. | 30 s client heartbeats keep it awake while anyone is connected; cron backstops idle periods. If both fail, the first message after wake is slow, not lost. |
| 0.1 CPU. | Text only; no media pipeline; single process. |
| Turso ownership change (Supabase acquisition). | Plain SQLite schema; portable to Postgres/Neon/Aiven with a small migration. |
| FCM dependency for closed-app notifications. | Unavoidable on Android; no alternative delivers to a killed app. |
| Transparent always-on-top window vs. exclusive-fullscreen games. | Popup suppressed in that case; toggle in settings. |
| Refresh token storage on Android is not hardware-backed. | Documented; acceptable for a private friend group. |
| 20-account ceiling assumed. | Schema and limits are sized for it; scaling beyond is a deliberate future project. |

## 14. Phases

Each phase ends in something runnable.

1. **Server** — workspace scaffold, schema + migrations, auth, conversations/messages/sync, WS hub,
   FCM sender, vitest suite green. Runs locally against a local libSQL file.
2. **Shared UI** — design tokens and glass components, login, list, thread, settings; wired to the
   local server through `WebSocketTransport`; verified in a browser.
3. **Desktop** — Electron shell, IPC transport, tray, popup window, settings, electron-builder
   installer; verified with the window closed.
4. **Android** — Capacitor shell, push registration, FCM payload handling, deep link, APK built and
   installed on a real phone.
5. **Deploy** — Render + Turso + cron backstop, environment variables, then the full manual
   verification list in §12 including a real cold start.
